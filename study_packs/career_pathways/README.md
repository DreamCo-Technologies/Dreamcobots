# Edu Career Pathways: majors to O*NET study plans

Maps bachelor's majors (2020 CIP codes) to O*NET-SOC occupations using the official O*NET CIP crosswalk, then writes one study plan per major (1,044 majors in two tiers, see Coverage): linked occupations with O*NET 31.0 Job Zones, the highest-importance O*NET knowledge areas and Essential Skills, 1 to 3 Job Zone-based entry-level targets, a 4-year outline, typical next steps, and 6 practice tasks with rubrics. The outline, next steps, and practice tasks are DreamCo-derived guidance, not O*NET data.

Fetch pinned sources: `python fetch_sources.py` (verifies sha256). Rebuild: `python build.py` (needs pandas, openpyxl, snowballstemmer (BSD-3-Clause); set `DREAMCO_GATE_TOOL` to `tools/license_provenance_gate.py` if it is not found automatically). build.py runs the gate with `--repo-root`: `DREAMCO_REPO_ROOT` if set, else the repo root two levels above this pack (the directory that contains `study_packs/career_pathways`), so the gate resolves evidence ids under `evidence_root`. Test: `pytest tests` (needs jsonschema for schema checks).

Inputs:
- `raw/` pinned official files (hashes in `raw/SOURCES.md`; raw data files are not committed).
- `authored/` checked-in DreamCo-authored sources that build.py reads, so builds are reproducible:
  - `practice_tasks_authored.json`: 162 practice tasks for the 27 authored majors. Each cites an O*NET 31.0 Task ID and O*NET-SOC code and has an original-wording paraphrase of the task's intent, an occupation-specific scenario prompt, a 3-criterion rubric for that scenario, and a reference answer outline.
  - `outline_topics.json`: per-major course-topic and practice mappings, keyed by CIP and O*NET element, for every element each authored outline uses.
  - `target_overrides.json`: manual entry-target overrides with reasons, plus review notes for majors kept as computed.
  - `coverage_rules.json`: which CIP codes get a plan (inclusion rule, excluded series, prefixes and title patterns, each with a reason).
  - `release_changes.json`: what changed versus the previous release (8cc1ce1), including each replaced practice-task citation with its reason; read by `regression.py`.
  - Authorship of all five: DreamCo-original, authored by Grok-Edu-Career-Pathways (AI), not human-reviewed.

Outputs:
- `data/major_to_onet.csv`, `data/majors_selected.json` (incl. tier, Job Zones, entry targets and target review), `data/practice_tasks.json`, `data/coverage.csv` (every CIP code in the crosswalk with included/excluded and the reason).
- `study_plans/<cip>_<slug>.md` (human layer) and sidecar folder `study_plans/<cip>_<slug>/` with `plan.json` (machine layer), `provenance.json`, `asset.json`, `candidate.json`, and `license_gate.json` (output of the DreamCo license/provenance gate).
- `data/dreamco_knowledge/evidence/regression/<asset_id>/<YYYYMMDD>-<NN>.json` (evidence record) and `.results.json` (item-level results), written by `regression.py`.
- Sources and hashes: `raw/SOURCES.md`. Test schemas snapshot: `tests/schemas/` (used when the live DreamCo schemas are not present).
- Data dictionary: `docs/DATA_DICTIONARY.md` (machine-readable `docs/data_dictionary.json`, generated by `docs/make_data_dictionary.py`) documents every output file and field; a test checks it against the outputs.
- Blind holdout grading kit (v3): `evidence/holdout_kit/` (see Method notes). `make_holdout_kit.py` draws it from an encrypted private source outside the repo (`holdout_crypto.py`); `score_holdout.py` checks a filled-in sheet (dry run), locks it (`--declare-final`) and scores it once with `--finalize`.

Method notes:
- Entry targets: a rule first picks linked occupations in O*NET Job Zone 4 (typical bachelor's level), excluding titles containing Manager, Chief, Postsecondary, or All Other (and Supervisor, Director, or Treasurers and Controllers unless nothing else is linked), base `.00` codes first, ranked by correlation with the eligible occupations' average knowledge profile; fallback Job Zone 3, then 5, then 1-2. Every authored major's result was then reviewed for plausibility: 11 majors have a documented override in `authored/target_overrides.json` (for example, Computer Science now targets Software Developers, Software QA Analysts and Information Security Analysts instead of Database Architects), and the other 16 have a review note. Pharmacy uses Job Zone 5 (Pharm.D.), and Criminal Justice uses a Job Zone 3 supervisor title with a caveat, because its only crosswalk links are supervisors, faculty, and an All Other code.
- Practice tasks reference an O*NET 31.0 Task ID and O*NET-SOC code. O*NET task text is not reproduced: tests check that no run of 5 or more words from any O*NET 31.0 task statement, Job Zone reference text, or occupation description appears in the authored fields or in the plan files (occupation titles excepted).
- Typical next steps cite O*NET Job Zone numbers only; Job Zone names and descriptions are not quoted.
- Knowledge and skill weighting (v4): the outline uses entry-weighted means of O*NET importance. Entry targets weigh 2. Other linked occupations in Job Zone 4 or 5 (or the targets' own Job Zone) weigh 1. Manager, Chief, Postsecondary-faculty, All Other, Supervisor, Director and Treasurers and Controllers titles, and non-target occupations in other Job Zones, weigh 0 (`build.WEIGHTING_METHOD`; the weights are in `plan.json` `knowledge_weighting`). Plans also show the unweighted mean over all linked occupations for comparison (`top_knowledge`, `top_skills`).
- Outline placement and skipped elements: English Language goes to Year 1 general education. Year 2 takes the first 3 core weighted elements and Year 3 the next ones by entry-target importance. Cross-cutting workplace knowledge (Customer and Personal Service, Administration and Management, Education and Training, Personnel and Human Resources, Administrative, Clerical) is skipped. There are two exceptions: it is core for the series where it is the subject (business 52, education 13, public administration 44: `build.CORE_BY_SERIES`), and an authored major's `authored/outline_topics.json` can keep it with a reason (`core_keep`). Elements that rank below the six knowledge course slots are skipped for capacity. Every plan lists the top elements it skips, with the reason, under the outline and in `plan.json` `outline_elements.skipped_knowledge`. For example, CS now covers Design and Telecommunications, and states why it skips Administration and Management.
- Licensing (v4): every item in `data/practice_tasks.json` carries its own `license` and `ownership_class`. Authored items are DreamCo-original (synthetic_generated_by_dreamco) and only reference O*NET identifiers. Generated items quote an O*NET task statement, so they are third-party CC BY 4.0 content (open_license_with_conditions), with license URL, attribution, a modification notice and the trademark notice. Their DreamCo template layer is listed separately. The file-level `ownership_class` (v5) is the most restrictive valid policy class among the items, open_license_with_conditions; `config/buddy-training-data-provenance-policy.json` lists the classes but does not rank them, so the order is documented in `build.OWNERSHIP_RESTRICTIVENESS` and `ownership_class_rule`. Per-item labels and `ownership_classes` by tier are kept. Each `plan.json` has a `license` block with attribution, required notices and per-field components. All plan-text notices are unchanged. DreamCo commercial terms for its own layer are not set (owner decision).
- Generated-tier plausibility checks (v5, automatic; `plan.json` `target_plausibility` and `quality_flags`, and a "Quality flags" section near the top of each generated plan):
  - Field fit (`build.FIELD_FIT_RULE`): TF-IDF cosine similarity between the CIP title's field terms (Snowball-stemmed, generic words such as science, studies, engineering and general ignored, compound words split into the stems they contain) and each linked occupation's O*NET 31.0 title, description and task statements. The pinned crosswalk has no CIP definitions, so the CIP title is the field description.
  - A rule target is dropped as clearly implausible only when its fit is 0, a same-tier linked occupation fits at least 0.02, it is a detailed specialty code (not `.00`) whose base `.00` occupation also fits 0, and it fits the titles of the program's 4-digit CIP series below 0.12 (`FIT_SERIES_KEEP`). Dropped targets are replaced from the rule's ranked tier with occupations whose fit is above 0. If none remain, the plan keeps fewer targets. Drops and additions are recorded in `target_plausibility` and as `quality_flags.actions`, and stated in the plan text. Example: Power Plant Engineering drops Robotics Engineers and Photonics Engineers and adds Solar Energy Systems Engineers.
  - Flags are only raised when a person needs to decide: `better_field_match_available` (a kept `.00` target fits 0 while a linked non-target fits at least 0.10) and `supervisory_task_kept`. Targets outside Job Zone 4 and fallback rules are `notes`.
  - The thresholds were set by inspecting this release's candidate drops; they are not validated. The v4 lexical `low_title_overlap` check is retired (`quality_flags.retired_checks`): it flagged 887 of 1,017 plans and changed nothing.
  - Practice tasks skip O*NET task statements that match a supervisory or managerial pattern (`build.SUPERVISORY_RULE`: supervise, provide supervision, direct and coordinate, direct the work of, manage staff, oversee staff, hire, subordinates, assign work to, evaluate the performance of, and train and supervise; "under supervision" is not counted). A plan keeps such a task only if fewer than 6 others exist, and flags it (none in this release).
  - Authored plans record supervisory citations as informational only, because their scenarios were written for them, and have no target_plausibility (their targets were reviewed).
- created_at in asset.json, plan.json, practice_tasks.json and the holdout kit is a full ISO 8601 timestamp with offset. Builds use a fixed release timestamp (`DREAMCO_BUILD_TIMESTAMP`, default 2026-10-02T18:30:00-05:00) so rebuilds are reproducible.
- Evidence ids `<kind>:<asset_id>:<run>` resolve to `<evidence_root>/<kind>/<asset_id>/<run>.json`. `asset.json` names `evidence_root` = `study_packs/career_pathways/data/dreamco_knowledge/evidence` (repo-relative), and the gate resolves it with `--repo-root`. Evidence is append-only: records are never deleted or rewritten once committed. `regression.py` refuses a run id already committed, and a test checks that every evidence file in any earlier commit is still on disk, unchanged.
- Blind holdout kit v3 (`evidence/holdout_kit/`, rubric discrimination), for the owner as the only available human grader. It has 18 new scenario prompts written for the kit only: 6 for Computer Science and 1 each for 12 other authored majors. A test checks that no 5-word run is shared with the published plans, `data/practice_tasks.json`, `authored/`, the READMEs and docs, the O*NET text, or the earlier v1 and v2 kits in git history. Each candidate answer has five labelled points. Some answers are full-strength and some are subtly weakened on one rubric criterion, with the same structure and length band. Which ones, and how many, is secret: `make_holdout_kit.py` draws the number of weakened answers from the private seed for every kit (`draw_weak`; Computer Science always gets at least one of each kind), and the drawn number is stored only in the encrypted key. The prompts, both answer versions and the answer key live outside the repository (`$DREAMCO_HOLDOUT_PRIVATE_DIR`, default `/workspace/edu-career-pathways-private`), encrypted at rest with AES-256-GCM (`holdout_crypto.py`; requires the `cryptography` package), with the passphrase outside `/workspace` and outside the repo (`/home/box/.ecp-holdout/passphrase`). They are never committed or synced. The kit README states the threat model: this stops a casual read of the private folder, not a deliberate decryption by an agent on the same box. `make_holdout_kit.py` draws with a seed from `secrets.randbits(128)` that is stored only in the encrypted key, so the key cannot be regenerated from committed inputs. Only `KEY_COMMITMENT.txt` is committed: the sha256 of the plaintext key, which contains a 256-bit random nonce, plus the sha256 of items.json. The v2 draw (16 items) was replaced before anyone graded it; because v2 is public in git history, all 18 v3 items are newly written rather than redrawn from v2.
  - `python score_holdout.py` (dry run) checks only that the sheet is complete and well formed. It never opens the key, prints no scores, and gives the same output for every complete sheet.
  - `python score_holdout.py --declare-final --grader "<name>"` (grader) writes `GRADING_FINAL.txt` with the sha256 of the graded sheet, which locks it.
  - `python score_holdout.py --finalize --run-id <YYYYMMDD-NN>` (builder) uses `/usr/bin/git` by absolute path with a sanitized environment (no inherited variables; empty temporary `HOME`; no system or global git config). It requires the canonical kit and output paths in a clone whose branch (`edu-career-pathways/majors-onet-study-plans` or `main`) has a remote that strictly normalizes to github.com/DreamCo-Technologies/Dreamcobots, with the sheet and `GRADING_FINAL.txt` tracked and clean. Their last commit (`grading_commit`) must be contained in the real remote tip from `git ls-remote`, checked in a fresh fetch (local refs never count; an unreachable remote is a refusal), and no commit reachable from the remote may already hold `FINALIZED.txt`, `REVEALED_KEY.json` or results for this key commitment; `REVEALED_KEY.json` must be absent at `grading_commit` and its ancestors, and the sheet and `GRADING_FINAL.txt` must not change on the remote after `grading_commit` (optional `--require-signer` also requires a signed grading commit that itself adds `GRADING_FINAL.txt` and changes the sheet). The sheet, `GRADING_FINAL.txt`, `items.json` and `KEY_COMMITMENT.txt` are then read once each with `git show <grading_commit>:<path>`, and those exact bytes are hashed and graded. It decrypts the key in memory, refuses a key that does not match `KEY_COMMITMENT.txt`, and writes `holdout:<asset_id>:<run>` records (human_evaluation, original_evaluation, split `holdout`, `baseline_score`, `grading_commit`, `remote_url`, `remote_branch`, `remote_tip_sha`, `test_only`, limitations built from the actual grader, `results_path` relative to the same repository root as `evidence_root`), then publishes the plaintext key as `evidence/holdout_kit/REVEALED_KEY.json` (nonce and seed included), to be committed with the results and `FINALIZED.txt` in one later reveal commit. After that is pushed, `--record-shas --run-id <run>` verifies the run and writes `evidence/holdout_kit/VERIFIED_SHAS.json` (grading_commit, reveal_commit, remote tip). `DREAMCO_HOLDOUT_TEST_ONLY_SKIP_GIT=1` or any change to `REMOTE_FETCH_URL` makes the run TEST ONLY with `passed: false`.
  - `python verify_holdout.py <record.json> [--repo-url URL] [--reveal-commit SHA] [--results FILE] [--expect-shas FILE|k=v,...] [--require-signer KEY] [--json]` (anyone but the scorer; stdlib only; exit 0 = accepted) and `verify_holdout.verify(record)` (importable API returning `accepted`, `ok`, `errors`, `checks`, `recomputed`, `shas`) independently check a record: ls-remote and a fresh fetch of the canonical repository, `grading_commit` reachable from the PR branch or `main`, `REVEALED_KEY.json` absent at and before `grading_commit` and added exactly once in a later descendant `reveal_commit` (never modified or re-added), the reveal the only commit touching that path on both allowed branches, the key's blob (`--find-object`) and nonce (`-S`) appearing under any path only in the reveal or its descendants, the sheet and `GRADING_FINAL.txt` byte-identical on every commit from `grading_commit` to `reveal_commit`, every results file and record for the key commitment in reachable history naming the same `grading_commit`, optional `--expect-shas` (recorded SHAs; detects a later force-push) and `--require-signer` (SSH or GPG signature on `grading_commit` from a registered key, and `grading_commit` must be the commit that adds `GRADING_FINAL.txt` and last changes the sheet; recommended, since every agent on the box pushes as ireanjordan24), the sheet, `GRADING_FINAL.txt` and `REVEALED_KEY.json` read with `git show` at the committed SHAs, `sheet_sha256` and the key commitment, and every score and the pass decision recomputed with its own implementation of the rule and required to match the record exactly. The scorer cannot prove its own push on a shared box; the trust rests on this verifier being run by someone else. See `evidence/holdout_kit/README.md`.
  - Pass rule: a record can pass only if the grader discriminated across the whole kit: detection rate at least 0.8 (a weakened item is detected when its weakened criterion is scored at most 1 and below the mean of its other two), false-alarm rate at most 0.2 (a full-strength item is flagged when its lowest criterion shows the same pattern), and mean gap (full-strength criterion scores minus weakened-criterion scores) at least 1.0 on the 0-2 scale. Given that, the asset needs, on its own items: at least 4 kit items with both kinds (single-item majors only count toward the kit-level check), a detection rate of at least 0.8, a false-alarm rate of at most 0.2, agreement of at least 0.8 with the key's accepted bands and strictly above its own `baseline_score`, and no full-strength item judged factually incorrect. Tests with made-up keys show that all 2s, the shortcut grader (one criterion marked 0 on every item) and a grader who is perfect on the other majors but gives all 2s on Computer Science pass no record in 2,000 random keys, that a perfect grader passes in all of them, and that an honest grader at about 95% detection passes Computer Science in most of them.
  - The v1 kit (12 items whose prompts and answers came from the published authored tasks, with `_key.json` committed) was deleted because it was not blind. It was never graded, and it was not evidence. No grades have been entered and no holdout evidence exists.
- Regression evidence: `python regression.py --baseline-ref 687b3c1 --repo <git clone of Dreamcobots> --run-id 20261002-04` compares each authored plan in this build with a baseline release, item by item. Run `-04` uses v3 (687b3c1), the last release whose regression evidence the merchant reviewed, as the baseline. It therefore spans both v4 and v5 changes; a v4 baseline would only add a second, shorter comparison. It checks linked occupation codes (title and Job Zone), knowledge and skill importance values and ranks, entry targets (presence and order), practice-task citations (practice id, O*NET-SOC code, task ID), that each citation is a real task of a linked occupation, license-gate checks (a check that passed must still pass), and O*NET text leakage in the plan (zero 5-word runs). Every difference must be explained by `authored/target_overrides.json` or `authored/release_changes.json`. Score = fraction of items that are preserved, improved, or changed with a reason; threshold 1.0, and any leakage fails the record. The record follows `config/evidence_provenance_schema.json` (source_type dreamco_experiment, transformation original_evaluation, source_reference = the asset's integrity_hash, integrity_hash = sha256 of the results file). build.py links every regression record of the asset whose integrity_hash matches its results file and that passed (v5: `-01` to `-04`, append-only). Older records keep the source_reference of the version they evaluated, and `asset.json` notes which ids evaluate the current version. Here those are `-03` and `-04`, because the authored plan files are unchanged since v4. Results files are deterministic: no run timestamp, and the gate file is hashed as canonical JSON without `evaluated_at`. The `synthesis_asset_record` check is not compared, because it depends on the linkage itself. The release order is build, regression, build (links the records and reruns the gate), then regression again as the last step, so `current.files` in every results file matches the files on disk. A rerun on an unchanged build reproduces each results file byte for byte. Tests verify every evidence record's integrity_hash against its results file, and the results' file hashes against disk. A test checks that the comparator flags dropped links, unexplained targets, changed scores, swapped citations, gate regressions and leaked text.
