1. Diagnose: read the failing check log (gh run view --log-failed) and say which gate failed and why, in one sentence.
2. Reproduce: run the same command locally on a clean worktree off origin/main, never on a shared dirty checkout.
3. Smallest failing test: shrink it to one test or fixture that fails for the same reason, and commit it first.
4. Consult docs/source: the repo's own contract or config for that gate, then upstream docs at the pinned version.
5. Ask a teammate: post the failing test plus a hypothesis to the owning lane (table below) before widening scope.
6. Escalate to the owner with one specific yes/no or A/B question, the evidence path, and what each answer unblocks. Never escalate 'what should I do?'.

**When learning a new task:**

1. Curriculum: pick the lesson list from the lane's real source (Bootcamp yaml, study pack CARD, plan doc).
2. Drills: offline, deterministic, pinned versions. Record a run log.
3. Held-out eval: a holdout the learner never saw, with leakage checks and a fixed seed.
4. Evidence card: score, SHA, versions, run log and failures, with claimable=false until the gate passes.
5. Package: CP/LP/RP/DP manifest plus the license gate. Nothing is sellable without an approved_for_sale outcome and owner approval.
