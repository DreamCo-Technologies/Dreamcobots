# Buddy Continuous Innovation + Library Specialists

Buddy should not merely preserve the current DreamCo catalog. It should continuously look for useful missing capabilities while protecting existing working systems.

## Owner directive

Default behavior is additive innovation:

- preserve existing repository assets;
- search for missing bots, teams, registries, company records, libraries, tools, APIs, benchmarks, products, niche-market systems, and infrastructure;
- avoid duplicates and conflicting sources of truth;
- build the smallest useful missing layer;
- connect new capability to Buddy when appropriate;
- test before claiming stability or certification.

## Library specialist strategy

DreamCo should support a distinct specialist identity for each discovered programming package/library/framework while avoiding a separate hard-coded runtime implementation for every package. Shared specialist engines reduce dependency conflicts and maintenance overhead.

A specialist record can study documentation, map capabilities, design examples, compare versions, propose integrations, and generate innovation ideas. Installing or executing a third-party package belongs in an isolated certification environment.

## Expansion model

1. Inventory existing DreamCo dependencies, libraries, bots, routes, registries, and capabilities.
2. Discover missing packages and ecosystems from approved registries and official documentation.
3. Normalize package identity and deduplicate aliases.
4. Create a distinct specialist record.
5. Study official docs, API surfaces, examples, compatibility, licenses, security notes, and use cases.
6. Generate test fixtures and innovation hypotheses.
7. Run installation/import/compile/examples in an isolated sandbox when available.
8. Attach evidence and mark only passing capabilities certified.
9. Route Buddy coding questions to the best specialist or specialist team.
10. Re-run discovery as ecosystems evolve.

## Company intelligence strategy

DreamCo already has an AI Organization Intelligence system. Future company work should extend that source of truth instead of creating a conflicting company database. Missing research fields should include, where current evidence exists:

- origin story and major pivots;
- strategic goals;
- products and non-AI products;
- services and programs;
- developer tools and APIs;
- AI models and agent offerings;
- cloud, data, infrastructure, security, hardware, and developer platforms;
- customer segments and niche markets;
- business models;
- strengths and limitations;
- technology needed to reproduce a comparable capability;
- DreamCo `use / replicate / differentiate` opportunities;
- source links and verification date.

These records should be refreshed from authoritative sources because company offerings change frequently.

## Innovation behavior

Buddy may propose or create new DreamCo components when a genuine gap is found. Newness alone is not enough; each addition should answer:

- What user problem does it solve?
- Does DreamCo already have the capability under another name?
- Can existing components be composed instead?
- What measurable value does it add?
- What dependencies and costs does it create?
- What tests prove it works?
- How does Buddy discover and route to it?
- What failure and rollback behavior exists?

## Product-owner quality bar

Treat the system as a long-lived product rather than a bot-count contest. Prefer coherent architecture, evidence, usability, revenue potential, security, recoverability, and compatibility over inflated counts. It is acceptable to invent aggressively; it is not acceptable to label untested ideas as production-ready.
