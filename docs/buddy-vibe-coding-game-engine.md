# Buddy Vibe-Coding Game Engine

Buddy's game builder should accept a plain-language idea and produce a benchmarkable game/simulation plan, then progressively build and verify it locally.

## Architecture

`idea → subject model → learning objectives → gameplay loop → world schema → rules → assets → interaction → simulation → UI → scoring → difficulty → telemetry → benchmark → sandbox → playtest → quality gate → export`

## AEC / interior-design bridge

Building models are especially valuable because structured BIM data can become interactive game worlds. Research demonstrates BIM/game integration for real-time visualization, navigation, accessibility, circulation, fire egress, building operation, and education. This makes construction, interior design, architecture, and blueprint data useful inputs for simulations.

## Any subject → simulation

For each subject Buddy generates:

1. Learning objectives.
2. World/environment model.
3. Player role.
4. Actions and tools.
5. Rules and constraints.
6. Consequences and feedback.
7. Scoring rubric.
8. Difficulty progression.
9. Failure/recovery states.
10. Benchmark evidence.

## Quality benchmark

Score 0–100 across visual fidelity, playability, mechanics, performance, stability, accessibility, audio, world consistency, AI behavior, UX, learning effectiveness, originality, and technical quality.

A reference game can establish a quality target, but Buddy must build original assets, mechanics, worlds, characters, code, and stories.

## Cost and independence

Free/local/open tooling is the default. Paid services require explicit approval. Every successful external-model-assisted task should create an opportunity for Buddy to implement a local/original capability and a permanent regression benchmark.
