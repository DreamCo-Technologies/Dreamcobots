# DreamCo Master Plan

## Objective

Unify the repository into one safe, evidence-driven Buddy system. Repository ideas remain discoverable, but only tested runtime evidence can establish capability or benchmark mastery.

## Operating rules

- Review branch and sandbox first.
- Preserve canonical capabilities and existing data.
- Prefer shared repairs over bot-specific duplication.
- Never weaken tests to obtain a pass.
- Never fabricate evidence.
- No production deployment, paid model/API calls, spending, account creation, external contact, or secret changes as part of repository remediation.
- GitHub Pages is the user-facing control and evidence surface; backend execution remains separately deployed or local.
- External writes and paid provider use require explicit approval.

## Capability truth states

`planned`, `cataloged`, `implemented`, `tested`, `sandboxed`, `connected`, `partially_connected`, `blocked`, `deprecated`, `duplicate`, `mastered`.

A catalog entry, route, profile, provider target, generated page, or remediation plan is not proof that the corresponding capability works.

## Benchmark closure loop

1. Measure current evidence.
2. Diagnose the root cause.
3. Choose the smallest shared safe repair.
4. Define rollback/fallback.
5. Apply only on the review branch or sandbox.
6. Run targeted tests.
7. Rerun the benchmark.
8. Compare before/after evidence.
9. Retest dependent suites when a shared component changed.
10. Repeat until acceptance criteria pass or the blocker is visible and actionable.

## GitHub Pages master surface

The Pages application should expose Buddy, capabilities, bots, divisions, tools, APIs, models, model progress, benchmarks, evidence, Actions, repository inventory, runtime bindings, backend health, sandboxes, forecasts, leads, Studio, personality/voice/image controls, avatar library, film/music workspaces, safety/consent, connections, datasets, and settings.

Every displayed capability should include its state, source, runtime binding, tests, benchmark evidence, dependencies, fallback, rollback, last verification, and blocker where applicable.

## Studio

Studio is the creative workspace for user-created personas and avatars. It supports configurable personality, voice, image, 2D/3D, cartoon, cinematic, game, film, television, animation, and music workflows.

Identity-linked voices and images require permission/provenance. Recognition is not permission. Revoked authorization must prevent future identity-linked generation.

The repository plan reserves 100 Hollywood/media tasks and 100 music-industry tasks. These are benchmark targets until executable acceptance tests and current evidence establish implementation.

## Model strategy

Buddy may route work to configured frontier, open, local, or specialized models. The UI must distinguish Buddy-native performance from model-assisted performance. Frontier routing can provide capability, but it does not prove Buddy itself has frontier-level mastery.

Provider setup remains lazy and user-controlled. Catalog metadata is not live connectivity. Live promotion requires comparable benchmark evidence.

## Master repository audit

Generate and continuously verify:

- canonical capability map
- runtime binding report
- duplicate-system report
- benchmark gap board
- Studio capability board
- Actions capability index
- Pages coverage evidence

The audit should identify missing links between files, runtime modules, tests, workflows, pages, APIs, and capabilities. It should never delete or overwrite canonical data merely to simplify the map.
