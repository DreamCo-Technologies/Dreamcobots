# Buddy GitHub Transition Contract

The long-term architecture is deliberately staged:

1. GitHub compatibility layer
2. Buddy becomes the primary human interface
3. DreamCo-native repositories and development workflows
4. Full migration without losing history or critical project metadata
5. Buddy becomes a multi-host open-source interface across GitHub, GitLab, Bitbucket, self-hosted Git and DreamCo

## Council rule

No single bot is production authority. Consequential changes can require architecture, security, testing, performance, compliance, cost and rollback review. Low confidence escalates to a human.

## Parity requirement

The platform must prove source control, collaboration, planning, AI coding, CI/CD, developer environments, packages, publishing, security, APIs/ecosystem, community, education, mobile, enterprise, observability, migration, reliability and cost-efficiency before claiming GitHub-replacement readiness.

## Product principle

Technical complexity is progressively disclosed. Beginners see goals and plain-language actions. Developers can open the complete underlying Git, CI, logs and configuration.

## Evidence principle

Feature inventory is not certification. Every green capability must point to executable tests, runtime evidence and, where appropriate, council evidence.
