# Buddy Frontier Growth + Universal Navigation Master Plan

## Product principle
Treat Buddy as a long-lived open-source learning system: protect its foundation, give it measurable curricula, let evidence—not hype—determine mastery, and preserve human approval for consequential actions. The goal is an intelligent adult/frontier-quality open-source system, not an autonomous system with unlimited authority.

## Repository parenting model

- **Foundation:** small, documented core; reproducible builds; pinned dependencies; signed/reviewed changes.
- **Memory:** versioned knowledge with provenance, retention rules, user controls and deletion.
- **Learning:** benchmark-first Bootcamp with regression tests and promotion gates.
- **Capabilities:** normalized capability graph shared by bots, tools, workflows and models.
- **Routing:** evidence-driven multi-agent teams; specialists can be selected per task step.
- **Sandbox:** deny-by-default tools/network, fixtures, synthetic data, kill switches and audit logs.
- **Governance:** security, privacy, legal/compliance and human approval gates.
- **Observability:** every capability has quality, speed, efficiency, reliability and safety evidence.
- **Recovery:** failed attempts become structured learning cases; successful repairs become regression tests.
- **Open-source health:** contribution docs, reproducible tests, issue triage, review automation and beginner-friendly workflows.

## Buddy navigation mission

Google Maps is the primary navigation provider where a user authorizes it. Buddy remains provider-aware so it can compare supported route providers and avoid vendor lock-in where feasible. Navigation must be hands-free-first: voice, steering-wheel controls, safe touch interactions and audio prompts should reduce phone handling while driving.

## Driver safety contract

While the vehicle is moving, Buddy should prioritize destination, turn instructions and safety-critical alerts. Nonessential screens should be deferred, summarized by voice, or queued. Music controls should use supported hands-free APIs. Buddy must never encourage interaction with a phone while driving.

A police/emergency scanner feature should only use lawful, authorized public feeds and must not interfere with emergency operations or enable evasion of law enforcement.

## Personal + business dashboard

Every user gets a customizable dashboard with capability cards. Merchants can connect supported business systems with explicit permissions. Buddy maps available data into a normalized schema and builds a custom dashboard without silently exporting sensitive information.

## Commerce intelligence

A commerce comparison layer should normalize products/offers from authorized data sources and compare total landed cost, shipping, fees, seller reliability, returns, availability and margin. Amazon FBA/Shopify opportunities are presented as research opportunities, never guaranteed profits.

## Professional network

Buddy can identify when a task needs a human professional and route the user to supported professionals. With explicit consent, completed professional work can become anonymized training/evaluation evidence. Professionals must control what proprietary information may be used for training.

## Creative studio

Buddy can support voice-driven music/beat creation, recording, video production and editing through licensed/authorized tools. Rights, attribution, consent and copyright checks are required before publishing or monetizing outputs.

## Travel

Buddy can compare authorized transportation and lodging options, assemble itineraries, track reservations and request bookings when the user explicitly authorizes the action and the connected provider supports it. It should never infer permission to spend funds merely from account balance.

## Professional pull-request review

Buddy's developer review mode should produce: change summary, risk map, architecture impact, security findings, test evidence, performance impact, dependency impact, regression risk, suggested fixes, reviewer questions, confidence and explicit approve/request-changes/comment actions. It should never merge code solely because an AI says it is safe.

## Issues intelligence

Builder bots should continuously classify issues into duplicate, obsolete, fixed, active, blocked, needs-human, needs-test, security-sensitive, product decision and documentation. The system should preserve evidence and links before closing/removing duplicates. It should never delete an issue solely because an agent thinks it is unnecessary; closure should retain a reason and reference to the canonical issue/commit.

## Mastery timeline

A system this broad is not responsibly estimated as a single date. Use measurable gates:

- **0–3 months:** navigation foundation, dashboard, model catalog, review/issue systems, sandbox contracts.
- **3–6 months:** provider adapters, hands-free navigation integrations, commerce/property/professional data layers, stronger Bootcamp.
- **6–12 months:** broad benchmark coverage, multi-agent routing maturity, real-world pilot evidence, large regression corpus.
- **12–24 months:** frontier-quality performance in selected domains if benchmark evidence supports it.
- **24+ months:** continuous open-source frontier program across an expanding capability graph.

"Mastered" means repeatable benchmark evidence at the chosen frontier/equivalent threshold, not elapsed time.
