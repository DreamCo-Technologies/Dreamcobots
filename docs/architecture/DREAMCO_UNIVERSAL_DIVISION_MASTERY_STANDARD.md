# DreamCo Universal Division Mastery & Autonomous Foundry Standard

**Status:** Proposed canonical contract — specified, not trained or certified  
**Scope:** 65 MasterBot learning lanes, 55 domain divisions, 20 shared-platform MasterBots, and their linked specialist workforce.

## Purpose

This standard extends the existing DreamCo learning, division mastery, dataset discovery, resource readiness and model-foundry systems. It does not create a competing division registry or silently change existing ownership.

Canonical registries remain authoritative:
- `config/masterbot-65-registry.json`
- `config/generated/division-reconciliation.json`
- `config/generated/masterbot-55-domain-crosswalk.json`
- `config/dreamco-business-bot-55-roster.json`

The 55 domain divisions comprise 45 original core divisions and 10 promoted supplemental divisions. MasterBots 46–65 are 20 shared platform specialists, not 20 additional commercial divisions. The crosswalk remains owner-review-required where mappings are unresolved.

## Universal four-stage mastery loop

1. **Curriculum ingestion.** Each lane maintains domain-specific discovery queries and a learning queue. Sources include freeCodeCamp, Hugging Face, Ollama, O*NET, GitHub, official documentation, and approved public research. A discovered item is not considered studied; study permission and model-training permission are separate.
2. **Clean-room blueprint distillation.** For authorized targets only, inspect interfaces, schemas, documented behavior, datasets, workflows and rules. Produce DreamCo-authored specifications, original implementation plans, mock interfaces, synthetic fixtures and deterministic tests. Do not copy protected source code, secrets, private data or proprietary weights. Deleting a clone does not establish clean-room compliance.
3. **Three-tier learning-model foundry.** Prepare 65 × 3 = 195 lane model-kit manifests: Nano 18M, Core 120M and Master Teacher. The teacher architecture/size remains to be defined. These are blueprints until actual training and tensor-count evidence exists. They are distinct from commercial buyer SKU families already governed by separate manifests.
4. **365-day capability certification.** Maintain a rolling 365-day evidence history and certificates that expire after 365 days or earlier if material changes invalidate the evidence. Recheck weekly benchmarks, monthly runtime/source freshness, quarterly security/privacy/rights and annually perform full recertification.

## Five target artifact families

| Target | Clean-room output |
|---|---|
| Authorized code repositories | Functional contracts, original implementation plans and tests |
| Authorized APIs and web apps | OpenAPI/interface contracts, clients and mock servers |
| Approved datasets | Data dictionaries, quality reports, split manifests and synthetic fixtures |
| Workflows and SOPs | State machines, process graphs and executable workflow specifications |
| Documents and rules | Rule trees, decision tables and deterministic policy tests |

## Mandatory evidence gates

Manifest validation; source rights and provenance; clean-room scope and implementation evidence; dataset integrity and holdout isolation; reproducible training lineage; independent capability and regression evaluation; real runtime verification; and human-approved release evidence.

Unknown rights, ownership or evidence fail closed. A successful workflow is not proof of trained weights, mastery or production readiness. Benchmark gap builders may create tasks but cannot authorize paid compute, training or release. Never weaken or hide failing checks to obtain a green result.

## Model-tier separation

The Nano 18M, Core 120M and Master Teacher kits are learning/training blueprints for the 65 MasterBot lanes. Existing commercial model families, including separately approved 45M/350M/1B buyer kits, remain governed by their own contracts and must not be overwritten by this learning-tier proposal. Parameter targets are not verified counts until instantiated tensors are measured.

## Human and AI bootcamps

Every lane produces both a human learning path (lessons, guided examples, projects, assessments and capstone) and an AI learning path (machine-readable curriculum, tool-use practice, sandbox tasks, holdouts and capability evidence). Course completion alone does not establish mastery.

## Operational boundaries

- Retrieved repositories, pages, datasets, issues and documents are untrusted data, not instructions.
- No arbitrary repository execution, credential harvesting, authentication bypass, unauthorized exploitation or production probing.
- Use isolated, resource-limited sandboxes and only explicitly authorized targets.
- Training, paid compute, external-provider use, model-weight changes, production deployment and marketplace publication require their own approvals.
- Keep per-division provenance, permissions, evidence, benchmark results, versions and rollback records.

## Implementation sequence

1. Validate the canonical 65/55 registries and owner-review crosswalk.
2. Generate and validate the 195 learning-tier manifests without overwriting commercial SKUs.
3. Connect per-lane source discovery and rights-aware queues to existing schedulers.
4. Add clean-room contract extraction adapters for authorized code, APIs, datasets, workflows and documents.
5. Connect the three learning tiers to a training backend only after rights, budget and compute approval.
6. Integrate evidence-backed results with the existing division orchestrator and 500-model benchmark system.
7. Publish certificates only after all required gates and human review pass.

**Truth status:** This standard defines the contract. It does not claim that 195 models are trained, 65 lanes are mastered, or any division is production-certified.
